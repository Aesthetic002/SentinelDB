1Who is actually running it?

The short answer: every node runs the whole algorithm for itself, and nobody is in charge of the nodes. There is no master program that decides who leads. The leader is whoever the nodes voted for most recently, and that can change at any moment.

Five copies of the same program

Each node is its own sentinel-node.exe process with the same code. Each one has its own clock, its own timers, its own copy of the data on its own disk, and decides for itself when to start an election.

The leader is elected, not appointed

One node at a time wins a majority vote. It is the only one that accepts writes and the only one that sends orders. If it goes quiet, the others notice on their own and elect someone else.

sentinel-lab is only a launcher

It starts the five processes with the right settings and stops them on Ctrl+C. In the web demo it also acts as a client and injects faults. It never votes, stores data or handles your SQL.

2What is running on the machine

When you run bin\sentinel-lab serve, this is what exists on your PC. In a real deployment, each of the five nodes would be on a different machine, and nothing else would change.

3Inside one node

Every node runs the same parts. A single loop owns the Raft state and is the only code allowed to change it, so there are never two threads arguing about who the leader is inside one process.

4Who commands whom

Orders flow one way: from the leader to the followers. Followers obey any leader whose term is at least as new as the one they know, and they only ever answer. They never give orders to anyone.

5A write, from your keyboard and back

Say you type UPDATE accounts SET balance_cents = 500 WHERE id = 1; and your CLI happens to be connected to n2, a follower. Press Next to follow it one step at a time.

Why the request ID matters. If the leader dies between step 7 and step 9, you never see “OK”, but the write may already be committed. The CLI retries on another node with the same request ID, r-42. The database remembers IDs it has already applied, so it reports success without applying the write a second time.

6A read

A SELECT doesn't need to go into the log, but the leader can't simply answer from memory either. It might have been replaced a moment ago without knowing it yet, and then it would return old data. So it checks first. This check is Raft's ReadIndex.

7The three roles a node can be in

Every node is always in exactly one of three roles. All five start as followers. What moves a node from one role to another is only what it sees itself: its own timer, and the messages it receives.

Some rules decide when a node gives its vote. A node votes yes only if all of these are true:

  • It hasn't already voted for someone else in this term. It writes its vote to disk before replying, so a restart can't make it forget.
  • The candidate's log is at least as up to date as its own: the last entry has a later term, or the same term and the log is at least as long.
  • It hasn't heard from a working leader within the last election timeout. This is called leader stickiness. It stops one flaky node from repeatedly removing a healthy leader. A planned handover is the one exception.

8An election, step by step

This follows what happens when the leader, n3, is killed (the Kill the leader now button in the demo). Nobody tells the other nodes. They work it out from the silence.

In the real cluster, all of this takes roughly as long as the shortest random timer: between 0.5 and 1 second. That's the gap you see on the demo's latency chart under Plain Raft.

9Why there can't be two leaders in one term

It comes down to simple counting. Winning needs 3 votes out of 5. Any two groups of 3 out of 5 must share at least one node, and that node votes only once per term.

The same counting keeps committed data safe. An entry counts as committed only once it's on a majority of disks. A candidate needs a majority of votes, and voters refuse a candidate whose log is behind theirs. So any new leader already has every committed entry.

One subtlety. Two nodes can both believe they are leader at the same moment, but only in different terms. A cut-off old leader may not have heard the news yet. It's harmless: it can't commit anything, because a majority has moved on to the newer term and will turn it down. The project's model checker explores millions of possible orderings of events and finds no case of two leaders in the same term.

10Handing over before the leader dies

Plain Raft only reacts once the leader has gone silent for 0.5–1 s. SentinelDB's leader also watches how its own heartbeats are doing. When its links to the followers are getting worse, it gives leadership away while it can still do so cleanly.

How the handover itself works

  1. The leader stops accepting new writes, so the target can catch up.
  2. It sends the target any entries it's missing.
  3. Once the target has the whole log, the leader sends it TimeoutNow.
  4. The target starts an election straight away, without waiting out its timer. The others vote in the normal way, and leader stickiness doesn't block this vote, because it was asked for on purpose.
  5. If none of this finishes within one election timeout, the handover is dropped and the old leader carries on.
Why a wrong prediction can't break anything. The predictor can only ask for a handover. The handover goes through the normal vote, with the same rules as any election. So the worst a false alarm can do is cause one unnecessary handover of about 0.2 s. It can never create two leaders or lose data.
